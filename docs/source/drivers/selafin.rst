================================================================================
Selafin/Serafin -- TELEMAC outputs format
================================================================================

.. shortname:: TELEMAC

.. built_in_by_default::

MDAL supports reading of the _Selafin/Serafin format generated by TELEMAC_.

A Selafin file stores an IPOBO array holding 0 for an interior node and the
boundary numbering for the others. TELEMAC uses it to attach boundary
conditions, so MDAL computes a real numbering on save instead of writing
zeros. The convention is:

* boundary edges are the mesh edges used by exactly one face; they form the
  closed contours of the mesh,
* every contour is walked from its south-west node, that is the node of
  minimum x+y, ties broken on the smallest node id,
* external contours are numbered counter-clockwise, islands clockwise,
* contours are emitted in depth-first order of the contour nesting, and
  contours at the same level are ordered by the same south-west key,
* the numbering is consecutive, 1 to NPTFR, over the contours in that order.

On the single-contour meshes of the test data, this reproduces exactly, node
for node, the arrays written by Janet, by TELEMAC-2D, by Fudaa-Prepro and by
the Malpasset reference file. The ordering of several contours is MDAL's own
convention: it is deterministic, but it has not been compared with a
multi-contour file written by a TELEMAC tool.

When an unmodified Selafin mesh is saved again, the IPOBO of the source file
is written as it is. This only applies to a numbering that can be trusted:
the stored array is reused when its non-zero entries are exactly the
permutation 1 to NPTFR, when that count matches IPARAM(8) if the file sets
it, and when the file is not a partitioned sub-domain, IPARAM(9) = NPTIR
being 0, since the IPOBO record of such a file holds the KNOLG array instead.
Anything else, including the all-zero arrays written by older versions of
MDAL, is recomputed.

Saving from QGIS always recomputes the numbering, because the mesh handed to
the driver is a new in-memory mesh rather than the file that was loaded. The
numbering depends on the geometry only, so an edit that does not touch the
boundary leaves it unchanged; moving the south-west boundary node, on the
other hand, shifts the whole numbering by one position. A boundary conditions
file (CLI/CONLIM) written for the previous numbering must then be generated
again: it would otherwise still load, NPTFR being unchanged, with every
condition attached to the wrong node.

A mesh whose boundary cannot be numbered is rejected instead of being written
with an all-zero IPOBO, which TELEMAC would read as a mesh without any
boundary node. This happens on a pinch point, where a boundary node joins two
parts of the mesh and belongs to more than two boundary edges, and on a
non-manifold edge shared by more than two faces. The save then fails with an
incompatible-mesh error naming the offending node or edge, and the file that
was to be replaced is left untouched.
